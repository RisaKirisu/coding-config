# Trigger Session Sync after saved changes

Portable DSH State remains in DSH's local file backends. Session Sync copies it to the Sync Store after DSH saves a completed turn or a relevant workspace or message-feedback change. This was chosen over a Postgres persistence adapter, shutdown hooks, and filesystem watching because DSH already reports when these changes are saved, local operation still works without the Sync Store, and DevVM does not need to replace DSH's persistence implementation. Version one relies on the Single Writer Rule and eventual rsync completion.

Amendment: the transfer semantics this left implicit are that Session Sync never merges and never deletes. DSH has no deletion path for durable state — archiving a session adds its id to the workspace unit's archive set while the session log and its workspace accounting slot remain, workspace deletion removes only the registration, and the attachment store exposes no delete, prune, or orphan sweep — so Session Sync propagates additions only: session logs and attachment objects transfer as a union, `storages/` units transfer as whole documents — newest-wins when this workstation was the last to exchange with the Sync Store, and remote-wins regardless of modification time when the store has moved ahead (ADR 0005), since the other workstation was then the legitimate writer and a fresh or offline registry must never replace theirs — projection-cache data is excluded, and no rsync deletion, tombstone, or lease exists on either side. Because session logs are append-only, a pull skips files newer on the receiver and never accepts a copy shorter than the local one, which bounds clock skew and interrupted writes. Under the Single Writer Rule these rules are sufficient, so a Postgres persistence adapter remains rejected on stronger grounds than in the original decision: it would convert Sync Store unavailability from Degraded Sync into an outage, force conflict handling back in the moment offline operation is wanted, weld DevVM to DSH's persistence internals, and still not cover content-addressed attachment objects.

Amendment (DSH 0.1.2-rc.1): DSH changed projection cache storage from a single `storages/session_projcache.json` document to per-session documents under `storages/session_projcache/sessions/<id>.json`. Because DSH cold session listing does not refold session logs larger than 1024 bytes, excluding projection cache left chat titles unrendered until opened. Each document is a non-authoritative, whole-record checkpoint keyed by an immutable session ID; it may be stale and is refolded when the session opens. Per-session projection documents therefore transfer as whole files in a dedicated projection pass (`storages/session_projcache/sessions/***` with `-az --update`, newest wins), `storages/session_projcache/***` is excluded from the whole-document storages pass, and the session/attachment union pass's `--append-verify` never carries projection documents: they are atomically rewritten records, so retaining a stale receiver prefix and appending a sender suffix would corrupt the JSON document.
