# Let the DSH plugin own Session Sync transfers

The shared DSH plugin is the single Session Sync engine: it holds the rsync filter set, invokes rsync inside the DevVM, pushes after DSH reports a saved change, keeps Sync Status, detects that the Sync Store has moved ahead, and provides the startup reconciliation as a guest startup script that the DSH Runtime launch command runs before `dsh web`. The Control Daemon keeps only what a process outside the DevVM must do: provisioning one shared credential and copying the SSH key into the DevVM, verifying Sync Store reachability during setup, sequencing the launch command so the startup script runs before `dsh web`, deleting Sync Store data for a Project, and reading Sync Status for the central UI. Reconciliation output reaches the Project Log through the launch command's existing stdout and stderr streams, so no separate event drain exists. Two engines existed before this decision — one in the daemon over `devvm exec rsync` and one in the plugin — and duplicating the filter set, the retry ladder, and the Dirty Local State marker across them produced silent loss: both wrote the same marker files, so a transfer could clear a mark for a change it never carried. The plugin side wins the engine because the triggers ADR 0001 depends on are emitted inside DSH, because rsync must read VM-local Portable DSH State anyway, and because the durability checkpoint it must wait for (`session/flush`, a real fsync of the session log) is only observable in process. Reconciliation runs as a separate process ahead of `dsh web` rather than inside the plugin's `apply()` because a plugin cannot guarantee it runs before DSH opens its durable state: Cordis expresses load order through service requirements and patch-list position rather than a pre-load hook, so ordering a reconciliation ahead of every state-loading plugin would be luck, not contract, and it would also place network transfer inside DSH boot. Reconciliation never blocks the launch: the startup script records its outcome in the status file and `dsh web` starts regardless, because the head sequence of ADR 0005 already prevents the divergence that a launch refusal used to guard against. A fresh workstation that cannot reach the Sync Store starts in Degraded Sync with its `storages/` pushes held, so its empty registry can never overwrite the store's, and a failed startup push starts the DSH Runtime as failed and is retried by the plugin after the next saved change. Consequence: the daemon never transfers Portable DSH State itself, knows nothing about rsync, and interprets nothing about reconciliation; it decides only when reconciliation runs.
