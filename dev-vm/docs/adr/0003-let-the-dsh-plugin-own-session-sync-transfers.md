# Let the DSH plugin own Session Sync transfers

The shared DSH plugin is the single Session Sync engine: it holds the rsync filter set, invokes rsync inside the DevVM, pushes after DSH reports a saved change, keeps Sync Status, and detects that the Sync Store has moved ahead. The Control Daemon keeps only what a process outside the DevVM must do: provisioning one shared credential and copying the SSH key into the DevVM, verifying Sync Store reachability during setup, gating DSH Runtime launch on startup reconciliation, deleting Sync Store data for a Project, reading Sync Status for the central UI, and draining plugin-written sync events into the Project Log. Two engines existed before this decision — one in the daemon over `devvm exec rsync` and one in the plugin — and duplicating the filter set, the retry ladder, and the Dirty Local State marker across them produced silent loss: both wrote the same marker files, so a transfer could clear a mark for a change it never carried. The plugin side wins the engine because the triggers ADR 0001 depends on are emitted inside DSH, because rsync must read VM-local Portable DSH State anyway, and because the durability checkpoint it must wait for (`session/flush`, a real fsync of the session log) is only observable in process. The daemon keeps the launch gate because a plugin cannot guarantee it runs before DSH opens its durable state: Cordis expresses load order through service requirements and patch-list position rather than a pre-load hook, so ordering a reconciliation ahead of every state-loading plugin would be luck, not contract. Consequence: the daemon never transfers Portable DSH State itself, and the plugin never decides whether the DSH Runtime may launch.
